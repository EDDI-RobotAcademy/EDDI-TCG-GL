# 백로그 작성 규칙 (R2 리팩토링)

> 언제 여는가: 백로그를 쓰다가 이렇게 쓰는 게 맞나 싶을 때.

R2 리팩토링의 모든 백로그 문서가 따르는 규칙이다.
새 백로그를 만들 때는 [_TEMPLATE.md](_TEMPLATE.md)를 복사한다.

백로그는 개발 작업 목록인 동시에 **관계자 간 의사소통 문서**다.
이 저장소는 주 개발자가 2명 이상이며(커밋 기준 Leejaelim 1,080, Sanghoon Lee 505),
작성자 본인이 6개월 뒤 다시 읽는 문서이기도 하다.

---

## 불변 원칙 — 백로그의 다섯 파트

> **모든 백로그는 예외 없이 다음을 갖는다.**
>
> ```
> 제목                 무엇을 달성하려는가
> Success criteria     그것을 이루려면 어떤 흐름이 필요한가   (번호 목록)
> To-do                그 흐름을 만들려면 무엇을 해야 하는가  (5개 초과 금지)
> Issue                작업하면서 실제로 무엇이 문제였나
> Review               그래서 결과가 어땠나
> ```
>
> **그리고 이것만으로 서로 다른 분야의 사람과 소통이 되어야 한다.**

```
제목  ─────▶  SC 1. 흐름  ─────▶  Todo 1. 그 흐름을 만드는 할 일
              SC 2. 흐름  ─────▶  Todo 2. …
              SC 3. 흐름  ─────▶  Todo 3. …

                작업 진행 ─────▶  Issue   막혔던 것
                작업 종료 ─────▶  Review  수치와 평가
```

**SC의 흐름과 Todo가 짝을 이룬다.** 흐름이 5개를 넘으면 Todo도 5개를 넘게 되므로,
그때는 작업이 너무 큰 것이다. 규칙을 어기지 말고 **작업을 쪼갠다.**

### 작성 시점

| 파트 | 언제 쓰는가 |
|---|---|
| 제목, Success Criteria, Todo | 작업 **시작 전** |
| Issue | 작업 **중** — 문제가 생길 때마다 |
| Review | 작업 **종료 후** |

### 개요, 목적, 범위는 별도 절로 두지 않는다

SC의 **1번 흐름**으로 넣는다. 별도 절로 두면 선택 사항처럼 보여 쓰지 않게 되고,
쓰지 않으면 왜 하는 일인지가 사라진다.

> 근거: 기존 백로그 네 건 중 `aoe_skill_sea_of_specter.md`에 개요가 없다.
> 필수라고 적어둔 절도 빠졌다.

```
### 1. 왜 하는지와 어디까지 할지를 정한다
- **문제** — …
- **목적** — …
- **기대 결과** — …
- **건드리는 것** — …
- **건드리지 않는 것** — … (사유 필수)
```

**1번은 항상 이 흐름이고, 마지막은 항상 동작 보존이다.** 그 사이가 실제 작업 흐름이다.

## 규칙 1. 파일명과 제목 양쪽에 티켓 번호를 넣는다

```
docs/refactoring/R2-{N}-{slug}.md

첫 줄:  # [ETWGL-R2-{N}] 제목
```

기존 백로그(`summoning_sickness.md` 등)는 문서 어디에도 티켓 번호가 없어
`ETWGL-R-49`와의 연결이 사람 기억에만 존재한다. 파일명만 있으면 문서를 열었을 때
안 보이고, 제목만 있으면 파일 목록에서 안 보인다. **양쪽 모두에 넣는다.**

---

## 규칙 2. 섹션 구성을 고정하고 노션에 붙여 넣을 수 있게 쓴다

```
# [ETWGL-R2-N] 제목
선행: … │ 후행: … │ 산출물: …

# Success criteria     1번 = 왜/어디까지,  마지막 = 동작 보존
# To-do                최대 5개
# Issue                작업 중 발생한 문제
# Review               수치와 평가
```

### 노션에 옮기는 방법

**편집기에서 파일을 열어 긁으면 코드 블록이 된다.** 편집기는 클립보드에 텍스트와
함께 HTML을 올리는데, 그 HTML에 고정폭 글꼴과 문법 강조가 들어 있어 노션이
코드로 판단한다. 마크다운 문법은 아예 해석되지 않는다.

셋 중 하나를 쓴다.

```
1. 터미널에서 출력해 긁는다            cat docs/refactoring/R2-1-....md
2. 클립보드에 텍스트만 올린다          cat ... | pbcopy
3. 노션에서 Import → Markdown 으로 파일째 올린다
```

3번이 가장 확실하다. 클립보드를 거치지 않아 표도 노션 표로 변환된다.

### 문서 형식

- 네 파트는 **H1**(`#`)으로 쓴다
- 항목은 `###` 제목이 아니라 **번호 목록**(`1.`)으로 쓴다
- 들여쓰기는 **공백 4칸**. 노션이 스스로 내보내는 형식과 같다
- **한 항목은 한 줄로 쓴다.** 줄바꿈으로 이어 쓰지 않는다
- To-do 체크박스는 `- [ ]`
- Review는 **표 두 개** - 수치표(항목 / 값 / 판단), 평가표(구분 / 내용)
- 번호 항목 사이에는 빈 줄을 둔다

> **왜 한 줄로 쓰는가.** 불릿 표시 없이 네 칸 이상 들여쓴 줄은 마크다운이
> 코드로 해석한다. 한 항목을 여러 줄로 나눠 쓰면 이어지는 줄이 그 조건에 걸린다.

`개요`, `범위`, `Technical Notes`를 별도 절로 두지 않는다.
개요와 범위는 Success criteria 1번으로, 구현 세부는 Issue와 Review로 흡수한다.

## 규칙 3. 마지막 흐름은 [동작이 달라지지 않는다]

기능 백로그의 목표는 *"이 기능이 동작한다"*지만,
**리팩토링의 목표는 "이전과 똑같이 동작한다 + 구조가 목표 상태다"** 이다.
그래서 마지막 흐름을 동작 보존에 쓴다.

```
✗  ### N. 행동 불변 검증              ← 절차 이름
⭕  ### N. 게임 동작을 건드리지 않는다   ← 필요한 흐름
```

- 코드를 건드리는 작업 — 마지막 흐름을 통째로 여기에 쓴다
- 문서만 만드는 작업 — 마지막 흐름의 Bullet 하나로 충분하다

확인 항목(`타입 검사`, `동작 확인 목록`)은 그 흐름을 만드는 **Todo**에 넣는다.

---

## 규칙 4. 동작 확인 목록은 [BEHAVIOR_CHECK.md](BEHAVIOR_CHECK.md) 한 곳에만 둔다

각 백로그는 **링크만** 건다. 9개 티켓에 복붙하면 항목이 어긋나고, 카드가 늘어
항목이 추가될 때 갱신이 누락된다.

---

## 규칙 5. SC는 흐름, Todo는 그 흐름을 만드는 할 일

| | 무엇을 쓰는가 | 형태 |
|---|---|---|
| **Success Criteria** | 제목을 달성하려면 **어떤 흐름이 필요한가** | 번호 절 + Bullet |
| **Todo** | 그 흐름을 만들려면 **무엇을 해야 하는가** | 번호 + 체크박스 |

SC는 체크리스트가 아니다. 완료 여부는 **Todo에 체크**하고, SC는 목표를
흐름으로 분해해 보여준다. 그래서 SC 항목에는 체크박스를 달지 않는다.

완료 판정은 **SC의 흐름이 실제로 성립하는가**로 한다. Todo에 남은 항목이 있어도
흐름이 성립하면 그 작업은 끝난 것이며, 남은 Todo는 다음 작업 후보가 된다.

> **완료 후 문제가 나오면 새 번호를 따지 않고 같은 작업의 fix 커밋으로 처리한다.**
> 단 그때 **놓쳤던 흐름이나 확인 항목을 SC, Todo에 되돌려 넣는다.**

근거: `ETWGL-R-53`은 완료 이틀 뒤 fix 커밋을 받았다. "광역 공격에도 상태이상이
적용된다"는 흐름이 SC에 없었던 것이 원인이다. SC가 자라야 같은 누락이 반복되지 않는다.

---

## 규칙 6. Todo는 번호 붙인 최상위 항목 5개 이하

각 항목 아래 세부는 체크박스로 둔다. 6개 이상이 되면 묶거나 다음 티켓으로 넘긴다.

**SC 에는 이 제한이 없다.** 흐름이 그만큼 필요하면 그만큼 쓴다. 지금까지 티켓이
대부분 다섯이라 SC 도 다섯인 줄 오해하기 쉬운데, 다섯은 [왜 하는지 - 확인 - 실행 -
검사 - 동작 보존] 이 다섯 단계로 떨어지는 작업이 많아서일 뿐이다.

판정 결과를 여러 표로 나누는 작업은 **표 하나가 흐름 하나**가 된다. 실제로 저장소
43개를 네 갈래로 가른 작업(R2-24)은 흐름이 아홉이다.

표를 흐름 안에 넣을 때는 번호 줄 바로 아래, 들여쓰기 없이 둔다. 네 칸 이상
들여쓰면 마크다운이 코드로 읽어 표가 되지 않는다.

---

## 규칙 7. 번호는 계획 시점에 예약하고, 착수한 번호는 바꾸지 않는다

계획을 세울 때 번호를 붙여두고, 그 번호로 커밋하고 문서를 만든다.

**착수한 번호는 바꾸지 않는다.** 커밋 메시지와 문서에 이미 그 번호가 박혀 있어서,
바꾸면 나중에 이력에서 그 작업을 찾을 수 없게 된다.

**아직 착수하지 않은 번호는 바꿔도 된다.** 조사하다 보면 계획 때 몰랐던 것이 나와
순서가 뒤집힌다. 실제로 죽은 코드인 줄 모르고 [두 화면을 합칠지 나눌지 판정] 이라는
작업을 세웠다가, 한쪽이 아무도 안 부르는 코드인 것을 확인하고 그 작업을 없앤 적이 있다.
그때는 [지우기] 를 앞으로 당기고 나머지를 뒤로 미는 것이 맞다.

바꾼다면 착수 전에 한 번에 바꾼다. 하나씩 밀면 선행과 후행이 어긋난다.

## 규칙 8. 커밋 형식

```
<type>: [EDDI] <설명> [ETWGL-R2-N]

type = refactor (기본) | feat | fix | chore
```

한 티켓이 여러 커밋에 걸치는 것은 허용하되,
**되돌릴 때 티켓 단위로 한 번에 되돌릴 수 있어야 한다.**

## 규칙 9. 선행 / 후행을 명시한다

제목 바로 아래 한 줄로 적는다.

```markdown
> 선행: `[R2-N](R2-N-slug.md)` │ 후행: `[R2-M](R2-M-slug.md)`
```

R2는 9개가 순서 의존적이다. 특히 **R2-3은 나머지 8개의 검증 수단**이므로,
순서를 모르고 R2-7부터 시작하면 자동 검증 없이 폴더를 옮기게 된다.

## 규칙 10. 사람 중심의 제목과 목적을 작성한다

제목과 개요만 읽어도 **개발자가 아닌 관계자가** 왜 이 작업을 하는지,
완료 후 무엇이 좋아지는지 이해할 수 있어야 한다.

### 제목 = 대상 + 목적/결과

기술 용어를 없애라는 뜻이 아니다. **기술 용어가 제목의 목적을 가리지 않게** 한다.

| | |
|---|---|
| ✗ | `EntityId 통합 — 도메인 식별자 명시화` |
| ✓ | `재접속 시 어떤 유닛의 상태를 복원할지 식별할 수 있도록 식별자 통합` |
| ✗ | `Battle Aggregate 추출` |
| ✓ | `전투 상태를 하나의 일관된 단위로 관리하도록 Battle 애그리관문 추출` |

개발자는 뒤쪽 기술 용어를 알아듣고, 비개발자는 앞쪽 목적을 읽는다.

### 개요 = 문제 → 목적 → 기대 결과

**[기대 결과]는 기능이 아니라 사람의 행동 변화로 쓴다.**

| | |
|---|---|
| ✗ | dependency-cruiser를 도입한다 |
| ✓ | 개발자가 폴더 구조를 바꿀 때 모든 import를 직접 검사하지 않아도 잘못된 의존 방향이 자동으로 발견된다 |

전자는 도구 이름이고 후자는 행동 변화다.

### [User Impact]라는 이름은 쓰지 않는다

내부 리팩토링 9개 중 사용자가 직접 체감하는 것은 R2-9(재접속) 정도뿐이다.
`User Impact` 칸을 두면 나머지 8개가 사실이 아닌 내용을 쓰게 된다.
**[기대 결과(Expected Outcome)]**가 범용적이다.

---

### 제목에 구현 세부를 쓰지 않는다

클래스 이름, 함수 이름, 개수는 제목에 쓰지 않는다. 백로그 제목은 개발자가 아닌 사람도
무슨 일인지 알아야 한다. 세부는 Success criteria 로 내린다.

```
쓰지 않는다   손패 저장소 두 개를 Cache, Store 로 개명
             화면을 다시 그릴 때 실제로 버리도록 dispose 호출 연결

쓴다          손패 저장소 이름 정리
             화면 자원 정리 실제 적용
```

무엇을 어떤 이름으로 바꾸는지는 그 티켓을 여는 사람만 알면 된다. 제목은 목록에서
훑는 자리라 [무슨 일인가] 만 있으면 된다.

---

## 규칙 11. 모든 계층의 제목이 사람 중심이어야 한다

규칙 10을 문서 제목에만 적용하면 부족하다. **SC 절 제목까지 사람 중심이어야**
필수 3요소만으로 소통이 성립한다.

```
문서 제목        무엇을 위한 작업인가          ← 모든 독자
SC 절 제목       끝나면 무엇이 참이 되는가      ← 모든 독자
SC 체크박스      그것을 어떻게 확인하는가       ← 모든 독자, 한 문장으로
Todo            다음에 무엇을 할 것인가        ← 개발자
```

**체크박스까지 사람이 읽는 문장이어야 한다.** 여기가 무너지면 앞의 두 계층을
아무리 잘 써도 문서를 안 읽게 된다.

### SC 절 제목은 라벨이 아니라 상태 서술문으로 쓴다

Success Criteria는 "성공의 기준"이다. 작업 항목의 분류명이 아니라
**완료 시점에 참이 되는 문장**이어야 한다.

| | |
|---|---|
| ✗ | `### 2. 규칙 4종` |
| ⭕ | `### 2. 지켜야 할 구조 규칙이 코드로 표현되어 있다` |
| ✗ | `### 1. 추적 가능성` |
| ⭕ | `### 1. 작업과 문서가 번호로 연결되어 흩어지지 않는다` |
| ✗ | `### 3. 아직 없는 경로에 대한 대응` |
| ⭕ | `### 3. 규칙이 실제로 동작함이 확인되었다` |

왼쪽은 개발자에게만 의미가 있고, 오른쪽은 누가 읽어도 "그래서 뭐가 됐는데?"에
답한다. **기술 상세는 그 아래 체크박스가 담당한다.**

### 행동 불변 검증 절도 마찬가지다

```
✗  ### N. 행동 불변 검증
⭕  ### N. 이 작업으로 게임 동작이 달라지지 않았다
```

### 체크박스는 수치 나열이 아니라 문장으로 쓴다

수치는 **산출물에** 두고, 백로그에는 그 수치로 **무엇을 할 수 있게 되었는지**를
쓴다. 백로그에 숫자를 복사해 넣으면 두 곳에서 어긋나기도 하고, 무엇보다
사람이 판단할 수 없어 읽지 않게 된다.

| | |
|---|---|
| ✗ | `- [x] 시나리오 3,838라인, let 53, const 677, 리스너 16, await 77` |
| ⭕ | `- [x] 지금 구조로 남은 카드 85장을 만들면 파일이 몇 줄이 되는지 계획서가 답한다` |
| ✗ | `- [x] 추정이 아니라 재현 가능한 명령으로 얻은 수치만 기록` |
| ⭕ | `- [x] 문서에 적힌 명령으로 누구나 같은 수치를 다시 뽑아볼 수 있다` |
| ✗ | `- [x] 규칙 1 — battle/domain/** → three 금지` |
| ⭕ | `- [x] 전투 규칙 코드가 화면 라이브러리를 쓰지 못하게 막는다 — 저장과 복원의 전제` |

세 가지를 지킨다.

1. **한 항목은 한 문장.** 가운뎃점으로 항목을 이어 붙이지 않는다
2. **사람이 판단으로 체크할 수 있어야 한다.** 열어보고 "그렇다/아니다"가 나와야 한다
3. **왜 그것이 필요한지를 붙인다.** 기술 규칙에는 `— 저장과 복원의 전제`처럼
   짧은 사유를 단다

식별자, 경로, 명령어는 그대로 써도 된다. **나열이 문제이지 기술 용어가 문제가
아니다.**

## 규칙 12. 표기

| 용도 | 쓸 것 | 쓰지 말 것 |
|---|---|---|
| 나열 구분 | `,` | `·` |
| 문서 안의 절 이름 인용 | `[하지 않을 것]` | `「하지 않을 것」` |
| 라벨과 값 | `선행: R2-2` | `선행 · R2-2` |

```
✗  현황 측정 · 진단 10건 · 목표 구조 · 예상 결과
⭕  현황 측정, 진단 10건, 목표 구조, 예상 결과

✗  [하지 않을 것] 절에 사유를 적는다          ← 꺽쇠
⭕  [하지 않을 것] 절에 사유를 적는다          ← 대괄호

✗  > 선행 · 없음 │ 후행 · R2-2
⭕  > 선행: 없음 │ 후행: R2-2
```

가운뎃점은 한 줄에 여러 개가 붙으면 어디서 끊어 읽을지 모르게 된다.
쉼표는 읽는 사람이 익숙한 구분자다.

### 숫자에는 무엇의 숫자인지 붙인다

숫자만 적으면 쓴 사람만 안다. 무엇을 셌는지 함께 적는다.
셋 이상이면 개수 대신 **목록을 적는다.**

| | |
|---|---|
| ✗ | `여덟 쌍을 판정한다` |
| ⭕ | `무덤과 로스트존의 파일 열두 쌍을 판정한다` + 무엇이 열두 쌍인지 목록 |
| ✗ | `저장소 8개` |
| ⭕ | `저장소 파일 8개 (네 폴더가 각각 인터페이스와 구현체를 하나씩 갖는다)` |
| ✗ | `나머지 34개 폴더` |
| ⭕ | `아직 옮기지 않은 전투 폴더 34개` |

**무엇을 셌는지 안 적으면 다른 곳에서 다르게 센다.** 실제로 같은 것을
한 문서에서는 [저장소 8개], 다른 문서에서는 [저장소 4개]로 적어 어긋난 적이 있다.
하나는 파일을, 하나는 폴더를 센 것이었다.

### 전문어를 쓰지 않는다

읽는 사람이 그 분야 사람이 아닐 수 있다. 뜻이 통하는 우리말이 있으면 그것을 쓴다.

| 쓰지 말 것 | 쓸 것 | 왜 |
|---|---|---|
| 회귀 | 동작 확인 | [되돌린다] 로 읽힌다. 되돌리기는 따로 있는 개념이다 |
| 프로브 | 일부러 규칙을 어긴 파일 | 무엇을 하는 것인지 안 보인다 |
| 게이트 | 관문 | |
| 리프 노드 | 다른 곳이 참조하지 않는 끝단 | |
| 임계 경로 | 가장 오래 걸리는 경로 | |
| 빈혈 모델 | 속이 빈 모델 | |

기술 용어를 아예 쓰지 말라는 뜻이 아니다. **그 말이 없으면 설명이 안 되는 경우에만**
쓰고, 처음 나올 때 한 번 풀어 쓴다. 애그리게이트, 바운디드 컨텍스트가 그런 경우다.

**같은 말이 두 뜻으로 읽히면 이름이 실패한 것이다.** 표준 용어라도 바꾼다.

## 규칙 13. Issue와 Review를 반드시 남긴다

### Issue — 작업하면서 실제로 무엇이 문제였나

계획대로 되지 않은 것, 도구가 예상과 다르게 동작한 것, 중간에 뒤집은 판단을 적는다.
**같은 함정을 다시 밟지 않게 하는 것**이 목적이다.

```
### 1. 〈발생한 문제〉
- **증상** — 무엇이 어떻게 잘못되었나
- **원인** — 왜 그랬나
- **처리** — 고쳤나, 우회했나, 다음 작업으로 넘겼나
```

문제가 없었으면 `없음`이라고 적는다. **빈 절로 두지 않는다** — 안 쓴 것인지
없었던 것인지 구분되지 않는다.

특히 **판단이 뒤집힌 것을 지우지 않는다.** 잘못된 판단이 왜 그럴듯했는지가
다음 사람에게 가장 쓸모 있다.

### Review — 그래서 결과가 어땠나

Todo가 "무엇을 했나"라면 Review는 **"그래서 어땠나"**다.

```
### 수치
| 항목 | 값 | 판단 |     ← 값만 적지 않고 그 값이 무엇을 뜻하는지 함께
### 구조 평가
- 잘 맞은 것 —
- 미흡한 것 —          ← 반드시 적는다. 없으면 평가가 아니다
- 다음 작업에 넘길 것 —
```

수치는 **값과 판단을 함께** 적는다. `repository 186개`만으로는 좋은지 나쁜지
알 수 없다. `186개 — 이름이 실제 책임과 맞지 않는다`여야 판단이 된다.

**[미흡한 것]을 비우지 않는다.** 잘된 점만 있는 Review는 평가가 아니라 보고다.

## 규칙 14. Type 과 Domain 을 따로 적는다

작업 하나에 Type 하나와 Domain 하나를 붙인다. **둘은 서로 다른 질문이다.**

```
Type     무엇을 바꾸는 작업인가
Domain   어느 영역을 건드리는 작업인가
```

한 칸에 섞으면 설계가 흐려진다. 실제로 섞어 썼다가 [Domain] 이라는 값이
DDD 의 도메인과 충돌해 무엇을 가리키는지 알 수 없게 된 적이 있다.

### Type

| Type | 무엇을 바꾼다 | 코드 변경 | 동작 확인 |
|---|---|---|---|
| Strategy | 무엇을 어떤 순서로 할지의 판단. 계획과 기준 | 없음 | 필요 없음 |
| Documentation | 문서와 일하는 방식. 백로그 형식, 작업 절차 | 없음 | 필요 없음 |
| Tooling | 개발 도구와 그 의존성. 검사, 스크립트 | 도구만 | 필요 없음 |
| Structure | 폴더와 모듈의 배치. 위치와 이름 | 위치와 경로 | 관련 항목만 |
| Rule | 전투 규칙과 상태. 계산과 판정 | 로직 | 전 항목 |
| Rendering | 화면에 무엇을 어떻게 그리는가 | 표시 방식 | 전 항목 |

### Domain

| Domain | 무엇 |
|---|---|
| Battle | 전투 |
| Deck | 덱 편성 |
| Collection | 보유 카드 |
| Shop | 상점 |
| Lobby | 로비 |
| Platform | 화면 그리기, 자원 읽기처럼 어느 영역에서나 쓰는 공통 바탕 |
| — | 특정 영역에 속하지 않는다. 문서, 도구, 작업 방식 |

`Platform` 은 도메인이 아니다. `core/`, `TextureManager` 처럼 전투에도 덱 편성에도
똑같이 쓰이는 바탕이다. 전투에서 문제가 드러났더라도 산출물이 여기 있으면 Platform 이다.
실제로 카드 메시가 안 치워지는 문제(R2-25)는 전투에서 드러났지만, 만든 약속은
덱 편성 화면도 그대로 쓸 수 있어 Platform 으로 적었다.

**Domain 은 DDD 의 도메인이다.** 화면 이름이 아니라 업무 개념의 묶음이다.
지금 이 저장소에는 도메인 객체가 사실상 없다. `entity/` 190개 중 대부분이
화면 객체와 좌표를 담고 있다. 그래서 Domain 이 지금은 [어느 영역의 일인가] 만
가리키고, 도메인 객체가 생기면 그 안에서 더 나뉜다.

### Type 고르는 순서

```
코드를 바꾸는가?
├─ 아니오
│   ├─ 코드를 어떻게 할지 정한다        → Strategy
│   └─ 일을 어떻게 굴릴지 정한다        → Documentation
└─ 예
    ├─ 개발 도구를 넣거나 고친다        → Tooling
    ├─ 전투 규칙이나 상태를 바꾼다      → Rule
    ├─ 화면 표시 방식을 바꾼다          → Rendering
    └─ 위치와 이름만 바꾼다             → Structure
```

### 두 갈래에 걸칠 때

**먼저 작업을 쪼갠다.** 두 갈래에 걸친다는 것은 작업이 두 개라는 뜻이다.
폴더를 옮기면서 로직도 고치면 Structure 이자 Rule 인데, 그러면 동작이
달라졌을 때 무엇 때문인지 가릴 수 없다.

쪼갤 수 없을 때만 **동작이 달라질 위험이 큰 쪽**으로 적는다.
Rule 이 Rendering 보다, Rendering 이 Structure 보다 위험하다.

### Domain 이 두 영역에 걸칠 때

**바뀐 모델을 가진 쪽으로 적는다.** 부르는 쪽은 필요한 것을 약속으로 선언할 뿐
소유하지 않는다. A 서비스가 C 도메인의 저장소를 부른다고 그 일이 A 의 것이 되지
않는 것과 같다.

```
약속(인터페이스)    부르는 쪽에 둔다. 무엇이 필요한지는 부르는 쪽이 안다
구현                모델을 가진 쪽에 둔다
Domain              구현이 있는 쪽. 즉 실제로 바뀐 쪽
```

계기와 소유를 가른다. [무엇 때문에 이 일을 하게 되었나] 는 계기고, Domain 은
[무엇이 바뀌면 이 산출물을 다시 열게 되나] 다.

실제 예. 죽음의 대지 연출이 상대 필드 에너지 패널 뒤에서 돌아 보이지 않았다. 고치면서
연출 쪽에는 [떨림과 손상 정도를 받는다] 는 약속만 두고, 그 약속을 해내는 패널은
필드 에너지 쪽에 만들었다. 연출이 그리는 부분은 한 줄도 바뀌지 않았다.

```
계기       연출이 가려졌다              Battle Animation
바뀐 것    패널을 그리는 방식            Battle Field Energy   ← Domain 은 이쪽
```

제목이 [연출이 보이도록 …] 으로 시작해 Domain 도 연출로 읽히지만, 제목의 앞은 왜
하는지고 뒤가 무엇을 하는지다. **Domain 은 뒤를 따라간다.**

### 애매한 것은 애매한 채로 남긴다

모든 작업이 딱 떨어지지는 않는다. 억지로 맞추기보다 **왜 애매한지를 그 작업의
Issue 에 적는다.** 같은 애매함이 여러 번 나오면 그때 갈래를 손본다.

---

## 규칙 15. 파일의 자리는 [누가 부르는가] 로 정하지 않는다

옮길 곳을 정할 때 던지는 질문은 하나다.

```
무엇이 바뀌면 이 파일을 고치게 되는가
```

[누가 이걸 쓰나] 를 물으면 안 된다. 쓰는 쪽과 바뀌는 이유는 다르다. 화면 버튼이
부른다고 그 파일이 화면 버튼의 일부인 것이 아니다.

### 실제로 틀린 예

R2-15 에서 스킬을 화면에 재생하는 코드를 액티브 패널 폴더에 뒀다. 액티브 패널이
부르기 때문이었다. 그런데 그 파일에는 전투에 속한 것이 하나도 없었다. 카드 번호도,
몇 번째 스킬인지도, 행동을 소모했는지도 모르고 화면만 만졌다. 연출이었으므로
연출 폴더로 되돌렸다.

부르는 쪽을 따라갔다면, 나중에 다른 화면이 같은 재생을 쓰는 순간 자리가 또 틀린다.

### 자리를 정하기 전에 확인하는 것

- 이 파일이 게임 규칙을 아는가. 카드, 턴, 행동, 체력 같은 것을 아는가
- 화면을 다시 그리면 없어도 되는 것인가, 재접속해도 남아야 하는 것인가
- 이 파일을 고치게 만드는 변경을 세 가지 적어보고, 그것들이 한 묶음인가

세 가지가 두 묶음으로 갈리면 **그 파일은 두 개다.** 옮기기 전에 나눈다.
옮길 곳을 못 정하겠다는 느낌 자체가 그 신호다. 규칙 14 의 [같은 이유로 바뀌는가]
와 같은 질문이고, 이 규칙은 그것을 배치에 적용한 것이다.

## 규칙 16. 이 게임에 없는 개념을 제목과 이름에 쓰지 않는다

제목과 클래스 이름에 쓰는 말은 **이 게임에서 실제로 뜻이 있는 말**이어야 한다.
일반적인 개발 용어라도 이 게임에 그런 것이 없으면 읽는 사람이 다른 것을 떠올린다.

### 실제로 틀린 예

R2-15 의 제목을 [스킬 사용의 순서와 카드 이동을 갈라낸다] 로 적었다. 읽는 사람은
스킬 1 을 먼저 쓰고 스킬 2 를 나중에 쓰는 차례로 이해했다.

이 게임에서 스킬을 한 번 쓰면 그 유닛의 행동은 끝난다. 이어질 차례가 없으므로
순서라는 것이 애초에 없다. 가리키려던 것은 스킬 한 번을 쓰는 동안 카드가
올라가고 효과가 돌고 내려오는 재생이었다. 제목을 [스킬 연출 패키지 조정] 으로,
클래스 이름을 SkillSequence 에서 SkillPlayback 으로 바꿨다.

### 확인하는 방법

이름에 쓴 말을 게임 안에서 가리켜 본다.

```
순서    스킬에 순서가 있나              없다. 한 번 쓰면 행동이 끝난다
연출    화면에서 벌어지는 일인가        그렇다
행동    유닛이 이번 턴에 쓸 수 있는 것  그렇다
```

가리킬 것이 없으면 그 말은 쓰지 않는다.

### 함께 조심할 말

이 저장소에서 실제로 오해를 부른 말들이다.

- **Animation** — 그리는 일과 옮기는 일을 함께 가리켜 왔다. 옮기기만 하면 Motion 을 쓴다
- **회귀** — 되돌린다는 뜻으로 읽힌다. 동작 확인이라고 적는다
- **Sequence, Order** — 이 게임의 스킬과 행동에는 이어지는 차례가 없다
- **Panel** — SkillPanelAnimator 는 패널을 건드리지 않았다. 카드를 옮겼다

새로 오해를 부른 말이 나오면 이 목록에 더한다.

## 규칙 17. 사용처와 중복은 세는 방법을 정해두고 센다

무엇을 지울지, 무엇을 한 곳으로 모을지는 **몇 곳에서 쓰는지**로 정한다.
그런데 세는 방법을 틀리면 답도 틀린다. 실제로 세 번 틀렸다.

### 사용처는 폴더 경로가 아니라 이름으로 센다

`animation/entity/AnimationType` 이라는 경로로 찾아 [아무도 안 쓴다] 고 판정했다.
실제로는 바로 옆 파일이 쓰고 있었다.

```
찾은 것    "animation/entity/AnimationType"      → 0곳
실제       import {AnimationType} from "../entity/AnimationType"    ← 1곳
```

**같은 폴더 안에서 부르면 경로에 폴더 이름이 나오지 않는다.** `../entity/` 로 적히기
때문이다. 파일 이름이나 클래스 이름으로 찾아야 안팎이 다 나온다.

### 자기 파일만 빼고 센다

한 번은 쓰는 쪽 폴더까지 검색에서 빼고 세어 [안 쓰는 코드] 로 판정했다. 그것 때문에
필요 없는 작업을 하나 만들었다가 버렸다.

**빼는 것은 자기 자신 한 파일뿐이다.** 다른 무엇도 빼지 않는다.

### 같은 값이 여러 곳에 있는지는 값으로 센다

카드가 스킬을 쓸 때 서는 자리의 좌표가 네 곳에 있었는데, 네 곳이 변수 이름을
서로 다르게 지어놨다.

```
SKILL_POSITION_Y = (0.5 - 0.78221649) * ...      1곳
skillPanelY      = (0.5 - 0.78221649) * ...      3곳
```

어느 이름으로 찾아도 넷이 다 나오지 않는다. **숫자 0.78221649 로 찾아야 넷이 나온다.**

같은 값이 흩어져 있는지 볼 때는 변수 이름이 아니라 값 자체로 찾는다. 이름은 지은
사람에 따라 다르지만 값은 같아야 동작이 같다.

### 안 쓰는 코드라고 판정하기 전에

지우거나 옮기기 전에 이 셋을 다 해본다.

```
파일 이름으로 찾는다        SlashCutEffect.ts
클래스나 함수 이름으로 찾는다  class SlashCutEffect
검색에서 뺀 것이 자기 파일 하나뿐인지 확인한다
```

셋 다 자기 파일만 나오면 안 쓰는 코드다. 하나라도 걸리면 살아 있다.

실제로 `ExplosionSlashCutEffect.ts` 는 셋 다 해도 자기 파일뿐이라 안 쓰는 코드였고,
`AnimationType.ts` 는 두 번째에서 걸려 살아 있었다. 같은 폴더에 파일 이름과
클래스 이름이 다른 것도 있으니 둘 다 찾는다.

## 규칙 18. 화면이 가려지는 문제는 무엇이 어느 층에 있는지부터 센다

[왜 저게 뒤에 그려지지] 를 짐작으로 고치면 화면을 여러 번 확인하게 만든다. 실제로
한 번 그렇게 해서 세 번 고치고 두 번 되돌렸다. 고치기 전에 아래를 센다.

### 이 게임의 화면은 두 층이다

```
document.body
├─ container
│   └─ <canvas>                          배경, 카드, 유닛, 연출이 여기 그려진다
└─ <div> position: fixed, zIndex 1000     필드 에너지, 턴 표시, 안내 문구, 모래시계
```

`renderOrder` 는 **캔버스 안에서의 순서**다. 캔버스 전체가 얹힌 조각 밑에 깔려 있어서,
캔버스 안에서 아무리 나중에 그려도 그 조각을 넘지 못한다.

### 세는 것 셋

```
캔버스 안인가, 위에 얹힌 조각인가     조각을 만드는 것은 DomFrameRenderer 다
자리를 지정했는가                    position 이 지정된 것은 지정하지 않은 것보다 항상 위다
그리는 순서가 몇인가                 renderOrder. 같은 캔버스 안에서만 뜻이 있다
```

**zIndex 0 은 [맨 아래] 가 아니다.** 자리를 지정한 요소는 0 이어도 지정하지 않은
요소보다 위에 그려진다. 아래로 내리려면 음수여야 한다.

### 연출을 다른 층으로 옮기기 전에

밑에 무엇이 그려져 있는지에 기대는 연출은 **옮길 수 없다.** 옮기면 그림이 달라진다.
재질을 열어 아래 둘 중 하나라도 해당하면 옮기지 않는다.

```
더해서 빛나는 것 (AdditiveBlending)     밑에 그려진 색에 더한다. 빈 층에는 더할 것이 없다
밑을 덮어 어둡게 하는 것                 게임 화면이 아니라 화면 위 정보까지 어두워진다
```

옮길 수 없다면 반대로 한다. **가리는 쪽을 캔버스 안으로 내린다.** 연출은 한 줄도
건드리지 않아도 된다.

### 옮겨 그릴 때는 원래 계산식을 그대로 옮긴다

얹힌 조각을 캔버스 안 그림으로 다시 만들 때, 자리와 크기 계산을 새로 짜지 않는다.
비슷한 이름의 값이 여럿이라 틀리기 쉽다. 실제로 글자를 세로 가운데에서 내리는 값을
[글자 크기의 0.1] 이 아니라 [패널 높이의 0.1] 로 잡아 숫자가 한참 아래에 찍혔다.
