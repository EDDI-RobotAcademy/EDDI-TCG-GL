# 백로그 작성 규칙 (R2 리팩토링)

R2 리팩토링의 모든 백로그 문서가 따르는 규칙이다.
새 백로그를 만들 때는 [_TEMPLATE.md](_TEMPLATE.md)를 복사한다.

백로그는 개발 작업 목록인 동시에 **관계자 간 의사소통 문서**다.
이 저장소는 주 개발자가 2명 이상이며(커밋 기준 Leejaelim 1,080 · Sanghoon Lee 505),
작성자 본인이 6개월 뒤 다시 읽는 문서이기도 하다.

---

## 규칙 1. 파일명과 제목 양쪽에 티켓 번호를 넣는다

```
docs/refactoring/R2-{N}-{slug}.md

첫 줄:  # [ETWGL-R2-{N}] 제목
```

기존 백로그(`summoning_sickness.md` 등)는 문서 어디에도 티켓 번호가 없어
`ETWGL-R-49`와의 연결이 사람 기억에만 존재한다. 파일명만 있으면 문서를 열었을 때
안 보이고, 제목만 있으면 파일 목록에서 안 보인다. **양쪽 모두에 넣는다.**

---

## 규칙 2. 섹션 순서를 고정하고 「범위」를 필수로 둔다

```
# [ETWGL-R2-N] 제목
> 선행 · 후행 · 계획서 링크        (한 줄)
## 개요            문제 → 목적 → 기대 결과
## 범위            ★ 리팩토링 전용
## Success Criteria
## Todo            최대 5개
## Technical Notes 선택, 맨 아래
```

기능 백로그는 "이걸 만든다"로 경계가 자명하지만, **리팩토링은 손대기 시작하면
어디까지든 번진다.** 「범위」가 그것을 막는 직접적인 장치다.

`Technical Notes`를 맨 아래 두는 이유: 개발자는 SC까지 읽고 바로 작업한다.
중간에 두면 Todo가 밀려나 읽히지 않는다.

---

## 규칙 3. Success Criteria의 마지막 절은 항상 「행동 불변 검증」

기능 백로그의 SC는 *"이 기능이 동작한다"*지만,
**리팩토링의 SC는 "이전과 똑같이 동작한다 + 구조가 목표 상태다"** 이다.

```markdown
### N. 행동 불변 검증
- [ ] `npx tsc --noEmit` 통과
- [ ] `npm run depcruise` 통과 (R2-1 이후)
- [ ] 회귀 체크리스트 전 항목 통과 → [REGRESSION.md](REGRESSION.md)
- [ ] 이 티켓으로 **동작이 달라진 지점 없음** — 달라졌다면 그 자체가 결함
```

---

## 규칙 4. 회귀 체크리스트는 [REGRESSION.md](REGRESSION.md) 한 곳에만 둔다

각 백로그는 **링크만** 건다. 9개 티켓에 복붙하면 항목이 어긋나고, 카드가 늘어
항목이 추가될 때 갱신이 누락된다.

---

## 규칙 5. SC는 완료 조건, Todo는 후속 개선

| | 의미 | 완료 조건 |
|---|---|---|
| **Success Criteria** | 이 티켓의 완료 정의 | 전부 `[x]` 되어야 완료 |
| **Todo** | 후속 개선 (다음 티켓 후보) | 남아 있어도 완료 |

> **완료 후 버그가 나오면 새 티켓이 아니라 같은 티켓의 fix 커밋으로 처리한다.**
> 단 그때 **SC에 누락됐던 항목을 반드시 추가한다.**

근거: `ETWGL-R-53`은 8/23 완료 후 8/25에 fix를 받았다. SC에
*"광역기 경로에도 상태이상이 적용된다"*가 없었던 것이 원인이다.
SC가 자라야 다음에 같은 누락이 나지 않는다.

---

## 규칙 6. Todo는 번호 붙인 최상위 항목 5개 이하

각 항목 아래 세부는 체크박스로 둔다. 6개 이상이 되면 묶거나 다음 티켓으로 넘긴다.

---

## 규칙 7. 번호는 계획 시점에 예약하고 재번호하지 않는다

```
R2 번호는 [INDEX.md](INDEX.md)에서 미리 할당한다.
순서가 바뀌어도 번호는 유지한다 — 커밋 메시지에 이미 박혀 되돌릴 수 없다.
작업이 취소되면 번호를 비워두고 재사용하지 않는다.
```

---

## 규칙 8. 커밋 형식

```
<type>: [EDDI] <설명> [ETWGL-R2-N]

type = refactor (기본) | feat | fix | chore
```

한 티켓이 여러 커밋에 걸치는 것은 허용하되,
**되돌릴 때 티켓 단위로 한 번에 되돌릴 수 있어야 한다.**

---

## 규칙 9. 선행 / 후행을 명시한다

제목 바로 아래 한 줄로 적는다.

```markdown
> 선행 · [R2-4](R2-4-battle-aggregate.md) │ 후행 · [R2-6](R2-6-state-pipeline.md)
```

R2는 9개가 순서 의존적이다. 특히 **R2-1은 나머지 8개의 검증 수단**이므로,
순서를 모르고 R2-4부터 시작하면 자동 검증 없이 폴더를 옮기게 된다.

---

## 규칙 10. 사람 중심의 제목과 목적을 작성한다

제목과 개요만 읽어도 **개발자가 아닌 관계자가** 왜 이 작업을 하는지,
완료 후 무엇이 좋아지는지 이해할 수 있어야 한다.

### 제목 = 대상 + 목적/결과

기술 용어를 없애라는 뜻이 아니다. **기술 용어가 제목의 목적을 가리지 않게** 한다.

| | |
|---|---|
| ✗ | `EntityId 통합 — 도메인 식별자 명시화` |
| ✓ | `재접속 시 어떤 유닛의 상태를 복원할지 식별할 수 있도록 식별자 통합` |
| ✗ | `Battle Aggregate 추출` |
| ✓ | `전투 상태를 하나의 일관된 단위로 관리하도록 Battle 애그리게이트 추출` |

개발자는 뒤쪽 기술 용어를 알아듣고, 비개발자는 앞쪽 목적을 읽는다.

### 개요 = 문제 → 목적 → 기대 결과

**「기대 결과」는 기능이 아니라 사람의 행동 변화로 쓴다.**

| | |
|---|---|
| ✗ | dependency-cruiser를 도입한다 |
| ✓ | 개발자가 폴더 구조를 바꿀 때 모든 import를 직접 검사하지 않아도 잘못된 의존 방향이 자동으로 발견된다 |

전자는 도구 이름이고 후자는 행동 변화다.

### 「User Impact」라는 이름은 쓰지 않는다

내부 리팩토링 9개 중 사용자가 직접 체감하는 것은 R2-6(재접속) 정도뿐이다.
`User Impact` 칸을 두면 나머지 8개가 사실이 아닌 내용을 쓰게 된다.
**「기대 결과(Expected Outcome)」**가 범용적이다.

## 독자별로 이 문서에서 답을 얻어야 하는 질문

| 독자 | 질문 | 답이 있는 절 |
|---|---|---|
| 기획 / PM | 왜 필요한가? 무엇이 끝나면 완료인가? | 제목 · 개요 · SC |
| 개발자 | 어디를 고치는가? 무엇을 안 건드리는가? 선행은? | 범위 · 선행/후행 · Todo |
| QA | 무엇이 기존과 같아야 하는가? 무엇을 테스트하는가? | 행동 불변 검증 · REGRESSION.md |
| 6개월 뒤의 본인 | 왜 이 결정을 했는가? 왜 여기까지만 했는가? | 개요 · 범위(건드리지 않는 것의 **사유**) |

마지막 행 때문에 **「건드리지 않는 것」에는 사유를 반드시 적는다.**
목록만 있으면 나중에 "왜 안 했지?"에 답할 수 없다.
