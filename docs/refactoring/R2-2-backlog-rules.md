# [ETWGL-R2-2] 작업의 목적과 범위를 나중에도 확인할 수 있도록 백로그 규칙과 템플릿 수립

선행: R2-1 │ 후행: R2-4 │ 산출물: 백로그 작성 규칙 13개와 다섯 파트 구조 (문서 파일은 R2-4 에서 완성)

# Success criteria

1.  왜 하는지와 어디까지 할지를 정한다
    - 문제
        - 지금 있는 백로그 네 건 중 어느 것에도 작업 번호가 없어서, 어떤 문서가 어떤 작업이었는지가 사람 기억에만 있다
        - 완료 판정 기준도 없어서 한 작업은 완료 선언 이틀 뒤에 수정 커밋을 받았다
        - 이 저장소는 주 개발자가 둘 이상이고, 작성자 본인도 시간이 지나면 판단 근거를 잊는다
        - 앞으로 작업이 여덟 건 더 나오는데 같은 방식이면 왜 했는지를 잃는다
    - 목적
        - 백로그를 작업 목록이 아니라 작업 명령서, 의사결정 기록, 의사소통 문서로 쓸 수 있도록 규칙과 템플릿을 정한다
    - 기대 결과
        - 개발자가 아닌 사람도 제목과 Success criteria만 읽고 왜 하는지와 끝나면 무엇이 좋아지는지 안다
        - 개발자는 어디를 고치고 무엇을 건드리지 않을지 문서에서 바로 확인한다
        - 6개월 뒤 본인이 다시 읽어도 왜 여기까지만 했는지에 답할 수 있다
    - 건드리는 것
        - 작성 규칙, 템플릿, 동작 확인 목록, 작업 번호표
    - 건드리지 않는 것
        - 기존 백로그 네 건의 소급 정리 - 이미 끝난 작업이라 지금 번호를 붙여도 얻는 것이 적다. 다시 열 일이 생기면 그때 붙인다
        - 이슈 트래커 연동 - 번호 체계를 외부와 어떻게 잇는지는 팀 합의가 필요하다
        - 커밋 메시지 형식 변경 - 541개 커밋이 이미 같은 형식이다. 바꿀 이유가 없다

2. 작업과 문서를 번호로 묶고 경계를 적게 한다
    - 파일 이름과 문서 제목 양쪽에 번호를 둬서 어느 쪽에서 찾아도 짝을 찾는다
    - 번호는 미리 정하고 나중에 바꾸지 않는다 - 커밋에 남은 번호와 어긋나지 않게
    - 앞뒤로 어떤 작업이 오는지 문서 첫 줄에 적는다
    - 무엇을 건드리고 무엇을 건드리지 않을지, 건드리지 않는 것에는 이유를 쓰게 한다

3. 완료 판정을 사람마다 다르게 하지 않는다
    - 무엇이 충족되면 끝인지 정한다
    - 리팩토링은 동작이 이전과 같다는 것까지 확인해야 끝난다
    - 확인 절차는 한 곳에만 두고 각 문서는 그것을 가리킨다
    - 완료 후 문제가 나오면 놓쳤던 항목을 그 문서에 되돌려 넣는다

4. 개발자가 아닌 사람도 읽을 수 있게 한다
    - 제목이 기술 용어가 아니라 목적을 먼저 말하게 한다
    - 절 제목과 항목까지 사람이 읽는 문장으로 쓰게 한다
    - 일이 끝나면 사람의 작업이 어떻게 달라지는지 쓰게 한다
    - 작업 중 막힌 것과 결과 평가를 남기게 한다 - 다음 사람이 같은 함정을 밟지 않도록

5. 다음 작업을 바로 시작할 수 있게 하고 게임 동작은 건드리지 않는다
    - 복사해서 쓸 템플릿을 둔다
    - 남은 작업의 순서와 서로의 의존 관계를 정리한다
    - 중간에 멈춰야 할 때 어디서 멈춰도 되는지 적는다
    - 규칙을 실제로 적용한 예시를 하나 남긴다 - 문서만 있으면 안 지켜진다
    - 문서만 추가하므로 게임 동작은 달라지지 않는다

# Issue

1. 규칙을 만들면서 규칙 자신이 세 번 바뀌었다
    - 증상
        - 처음에는 절 네 개로 시작했다가 여덟 개로 늘렸다가 다섯 개로 줄였다
        - Success criteria의 뜻도 두 번 바뀌었다
    - 원인
        - 소통이 되게 하자는 목표를 절을 추가하는 것으로 풀려 했다
        - 절을 늘릴수록 안 쓰게 된다는 점을 놓쳤다
    - 처리
        - 절 수를 늘리는 대신 각 절의 내용이 소통하게 바꿨다
        - 제목, 절 제목, 항목까지 전부 사람이 읽는 문장으로 쓰는 규칙이 그 결과다

2. Success criteria를 완료 체크리스트로 잘못 잡았다
    - 증상
        - 처음에 [완료 시점에 참이 되는 상태] 로 정의하고 체크박스를 달았다
        - 그러면 To-do와 역할이 겹친다
    - 원인
        - 성공 기준을 다 됐는지 확인하는 목록으로 봤다
    - 처리
        - [제목을 달성하려면 어떤 흐름이 필요한가] 로 정정하고 체크박스를 뗐다
        - 결과적으로 흐름 수와 To-do 수가 맞아떨어져, 흐름이 다섯 개를 넘으면 작업을 쪼개야 한다는 신호가 자동으로 생겼다
        - 실제로 이 문서가 여섯 흐름이었다가 다섯으로 줄었다

3. 개요와 범위를 별도 절로 뒀다가 되돌렸다
    - 증상
        - 개요와 범위를 권장 절로 뒀는데, 그러면 쓰지 않을 가능성이 높다
    - 원인
        - 기존 백로그 네 건 중 하나가 이미 개요를 빠뜨렸다. 필수라고 적어둔 절도 빠진다
    - 처리
        - Success criteria의 1번 흐름으로 넣었다
        - 구조상 첫 번째로 오므로 건너뛸 수 없다

4. 표기가 섞여 있었다
    - 증상
        - 항목 구분에 가운뎃점을 쓰고 절 이름 인용에 꺽쇠를 썼다
        - 한 줄에 가운뎃점이 여러 개 붙으면 어디서 끊어 읽을지 알기 어렵다
    - 원인
        - 기계가 읽기 좋은 형태로 썼다
    - 처리
        - 쉼표와 대괄호로 통일했다
        - 268곳을 바꿨고, 그중 세 곳은 자동 치환이 잘못돼 다시 손봤다

5. 노션에 붙여넣으면 코드 블록이 되었다
    - 증상
        - 문서를 노션에 복사해 넣으니 내용 전체가 코드 블록 안에 들어갔다
        - 들여쓰기와 줄바꿈까지 사라진 채로 붙여졌다
    - 원인
        - 처음에는 문서 형식 문제로 보고 들여쓰기를 세 번 바꿨으나 증상이 같았다
        - 형식을 바꿔도 결과가 같으면 형식이 원인이 아니다
        - 실제 원인은 편집기에서 긁은 것이다. 편집기는 클립보드에 텍스트와 함께 HTML을 올리는데, 그 HTML에 고정폭 글꼴과 문법 강조가 들어 있어 노션이 코드로 판단한다
    - 처리
        - 터미널에서 출력해 긁거나, 노션의 Import → Markdown 으로 파일째 올린다
        - 문서 형식은 공백 4칸으로 되돌렸다. 노션이 스스로 내보내는 형식과 같다
        - 한 항목을 한 줄로 쓰는 규칙은 유지한다. 이건 별개로 옳은 규칙이다
