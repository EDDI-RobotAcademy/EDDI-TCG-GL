# [ETWGL-R2-1] 폴더 구조를 바꿔도 잘못된 의존이 자동으로 발견되도록 의존성 검사 도입

> 선행 · 없음 (R2 최초 티켓) │ 후행 · [R2-2](INDEX.md) │ 계획서 · [0-1단계](../battle_field_refactoring_plan.md)

## 개요

**문제.** 이 저장소에는 의존 방향을 검사할 수단이 없다. eslint · dependency-cruiser
모두 미설치이고 `npm test`는 exit 1 스텁이다. `tsc --noEmit`은 도메인 코드가
렌더링 라이브러리를 가져다 써도 통과시킨다. 지금까지 Frame 파일 31개가 THREE를
한 번도 import하지 않은 것은 순전히 사람의 규율 덕분인데, 앞으로 240개 폴더 중
31개를 옮기는 동안 규율만으로는 지킬 수 없다.

**목적.** 코드 구조가 지켜야 할 규칙을 문서가 아니라 **자동 검사로** 바꾼다.

**기대 결과.** 개발자가 폴더를 옮기거나 새 코드를 추가할 때, 모든 import를 사람이
직접 훑어보지 않아도 잘못된 의존 방향이 즉시 발견된다. 리팩토링 도중 구조가
조용히 무너지는 것을 막고, 이후 R2-2~R2-9 여덟 개 티켓이 **자동 검증 위에서**
진행된다.

대상 시나리오: `npm run draw-field-energy-full-efr`

## 범위

### 건드리는 것
- `dependency-cruiser` 개발 의존성 추가
- `.dependency-cruiser.js` 규칙 파일 신설
- `package.json`에 `depcruise` 스크립트 추가
- 아직 존재하지 않는 경로(`src/battle/domain/` 등)에 대한 규칙 선반영

### 건드리지 않는 것
- **소스 코드 한 줄도 수정하지 않는다** — 이 티켓은 검사 도구만 추가한다.
  기존 위반이 발견되어도 이 티켓에서 고치지 않고 해당 티켓으로 넘긴다.
  도구 도입과 위반 수정을 한 커밋에 섞으면 되돌릴 수 없다
- **eslint 도입** — 코드 스타일은 이번 리팩토링의 문제가 아니다.
  의존 방향만 검사한다
- **CI 파이프라인 구성** — 로컬 스크립트로 충분하다.
  CI는 팀 합의가 필요하므로 별도 논의
- **기존 240개 폴더의 위반 전수 조사** — 규칙은 `battle/` · `platform/` ·
  컨텍스트 경계에만 건다. 나머지는 해당 영역을 손볼 때 규칙을 확장한다

## Technical Notes

### 규칙 파일 위치
`.dependency-cruiser.js` — 저장소 루트.

### 경로 규칙의 시점 문제
규칙 1·4가 가리키는 `src/battle/domain/`은 R2-4에서 생긴다.
dependency-cruiser는 매칭되는 모듈이 없으면 그냥 통과하므로 **미리 넣어도 안전**하며,
오히려 R2-4 착수 시점에 규칙을 새로 쓰는 것보다 낫다 —
그때는 이미 코드를 쓰고 있어서 규칙이 사후 승인이 된다.

### 검사할 수 없는 것
- **GLSL 셰이더** — 런타임 컴파일. `tsc`도 webpack도 통과시킨다
- **`userData` 오용** — 타입이 `any`라 정적 검사 불가
- **싱글톤 증가** — `getInstance` 호출 수는 규칙으로 막기 어렵다 (현재 1,559회)

이 세 가지는 자동 검사 밖이므로 리뷰와 회귀 체크리스트에 의존한다.
