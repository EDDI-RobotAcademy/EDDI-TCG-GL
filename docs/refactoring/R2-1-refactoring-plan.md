# [ETWGL-R2-1] 리팩토링을 왜 어떻게 할지 판단할 수 있도록 현황 분석과 계획 문서화

선행: 없음 (R2 최초 작업) │ 후행: R2-2 │ 산출물: docs/battle_field_refactoring_plan.md │ Type: Strategy │ Domain: Battle

# Success criteria

1. 왜 하는지와 어디까지 할지를 정한다
    - 문제
        - 카드 12장을 만드는 동안 시나리오 파일이 2,044줄에서 3,838줄로 커졌고, 카드 한 장 추가 비용이 30~90줄에서 170~500줄로 늘고 있다
        - 남은 카드가 85장인데 이대로면 파일이 16,000~28,000줄이 될 가능성이 높다
        - 그런데 이 상황이 얼마나 심각한지, 무엇부터 손대야 하는지 판단할 근거가 없다
        - 근거 없이 시작하면 범위가 번지거나 엉뚱한 작업을 할 가능성이 매우 높다
    - 목적
        - 현재 구조의 문제를 측정값으로 정리하고, 어떤 순서로 무엇을 고칠지와 무엇을 하지 않을지를 문서로 확정한다
    - 기대 결과
        - 이 문서 하나로 왜 시간을 들이는지, 어디까지 하고 멈추는지, 지금 작업이 전체 어디쯤인지 판단할 수 있다
        - 작업 중 범위가 흔들릴 때 되돌아올 기준점이 생긴다
    - 건드리는 것
        - 리팩토링 계획서 신설
    - 건드리지 않는 것
        - 소스 코드 전체 - 분석과 실행을 한 작업에 섞으면 무엇을 근거로 고쳤는지 추적이 끊긴다
        - 덱, 컬렉션, 상점, 로비 화면 분석 - 배틀 필드가 지금 병목이다. 나머지는 그 화면을 손볼 때 같은 방식으로 한다
        - 서버 연동 설계 - 결정이 더 필요하고 지금 확정할 이유가 없다. 경계만 표시한다

2. 현재 상태를 숫자로 파악한다
    - 시나리오 파일이 얼마나 크고 무엇으로 채워져 있는지 파악한다
    - 카드가 몇 장 남았는지, 한 장당 비용이 어떻게 변해왔는지 커밋 이력에서 뽑는다
    - 누구나 같은 값을 다시 뽑을 수 있도록 측정 방법을 함께 적는다

3. 측정값에서 원인을 분리한다
    - 증상이 아니라 원인 단위로 나눈다
    - 각 원인이 어느 코드에서 비롯되는지 짚는다
    - 짐작이 아니라 기록으로 이미 일어난 사고를 근거로 삼는다

4. 목표 구조와 작업 순서를 정한다
    - 최종 폴더 구조, 어떤 데이터를 어디에 둘지 판단하는 기준
    - 전투 처리 순서와 저장 형식 - 카드 85장이 같은 방식으로 만들어지도록
    - 무엇부터 손댈지와 그 이유, 중간에 멈춰도 되는 지점

5. 판단 근거를 남기고 게임 동작은 건드리지 않는다
    - 검토했으나 고르지 않은 방안도 기록한다
    - 논의 중 뒤집힌 판단도 지우지 않는다
    - 문서만 추가하고 소스 코드는 건드리지 않는다

# Issue

1. 상태 분류를 한 번 잘못 잡았다

        - 그러면 저장할 필요가 없다는 결론이 나온다
    - 원인
        - 전투를 한 판 하고 끝나는 것으로 보고, 플레이 도중 접속이 끊길 수 있다는 조건을 빠뜨렸다
    - 처리
        - 분류를 [Battle State, 영속] 으로 정정했다
        - 이 정정이 연쇄로 세 가지를 바꿨다
        - 저장 형식이 필요해지고, 유닛 식별자 통합이 [나중] 에서 [필수 선행] 으로 올라가고, 연출과 상태 변경을 분리해야 한다는 요구가 생겼다

2. 저장소 이름 정리를 두 갈래로만 나눴다

    - 원인

    - 처리
        - Repository, Store, Cache 세 갈래로 정정했다

3. 계획서가 한 번에 커졌다
    - 증상
        - 추가적인 작업을 진행하며 248줄에서 858줄로 자랐다
