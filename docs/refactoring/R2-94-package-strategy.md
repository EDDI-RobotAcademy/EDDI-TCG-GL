## 기존 방식과 지금 방식의 차이

패키지를 바꾸기 전에, 리팩토링으로 무엇이 이미 달라졌는지 적어 둔다. 남은 일이 무엇인지
알려면 어디까지 왔는지부터 보여야 한다.

| | 기존 방식 | 지금 방식 |
| --- | --- | --- |
| 전투가 무엇인가 | 어디에도 없다. 저장소 여덟 곳에 값이 흩어져 있다 | 전투 한 판을 담은 파일 27개. THREE 도 무작위도 시계도 없다 |
| 사용자가 한 일 | 화면이 저장소를 하나씩 고친다 | 명령 열하나로 전투에 말하고, 일어난 일 여덟 가지를 돌려받는다 |
| 카드 능력 값 | 확인용 화면 파일 하나에 흩어져 있다. 카드를 더할 때마다 그 파일이 커진다 | 값으로 적힌 카드 열넷. 카드를 더하는 일이 값을 적는 일이 된다 |
| 유닛 | 유닛이 화면 덩어리를 들고 있다 | 유닛은 번호와 체력만 든다. 그리는 것은 렌더러가 든다 |
| 카드를 그리는 곳 | 서비스가 직접 그린다 | 렌더러가 만들고, 다시 재고, 놓아준다 |
| 자리 값 | 그리는 코드 안에 섞여 있다 | 프레임에 값으로 적혀 있다 |
| 카드 옮기기 | 같은 일을 하는 코드가 네 벌. 걸리는 시간도 제각각 | 한 벌. 시간과 곡선은 부르는 쪽이 정한다 |
| 연출 | 그림을 화면에 바로 붙인다. 창 크기를 안 따라간다 | 겹에 담아 창 크기를 따라간다. 열넷이 같은 것을 쓴다 |
| 순수함을 지키는 것 | 사람이 지키는 약속 | 검사가 돈다. 파일 57개 |

**아직 안 된 것.**

앞의 넷은 R2-96 부터 R2-102 까지 할 일이다. 마지막 것은 R2-103 이다.

**카드가 늘면 화면이 함께 늘어난다.**

카드 한 장이 어디에 얼마나 적혀 있는지 세었다.

| 어디 | 카드 열두 장이 차지하는 것 | 카드가 늘면 |
| --- | --- | --- |
| 카드 능력 값 | 값 열넷 | 줄만 늘어난다 |
| 전투 상태 | 갈래 여덟 | 갈래가 늘지만 한 곳이다 |
| 화면 | 마흔여섯 곳. 1,832~4,063줄에 흩어져 있다 | 장당 약 네 곳씩 |

앞의 둘은 괜찮다. 카드를 더하는 일이 값을 적는 일이 된다. 화면이 문제다. 이 비율이면
100장에 약 400곳, 300장에 약 1,200곳이고, 한 자리에 모여 있지도 않다. 한 장을 더할
때마다 네 곳을 찾아 넣어야 하고, 하나 빠뜨리면 카드가 반만 동작한다.

R2-58 에서 [무엇을 고르는가] 와 [얼마인가] 는 값으로 옮겼지만 [무엇이 일어나는가] 는
못 옮겼다. R2-65~R2-68 에서 여덟 장의 판정을 전투로 넘겼어도, 연출을 언제 어떤 순서로
트는지는 화면에 남았다.

화면에 남은 카드별 갈래는 대체로 넷이다.

| 갈래 | 무엇 |
| --- | --- |
| 어디에 떨어뜨릴 수 있나 | 손패에서 끌어다 놓을 때 |
| 어떤 연출을 트나 | 연출 고르기 |
| 몇 번 고르게 하나 | 시체 폭발, 네더 블레이드 |
| 무엇을 덧붙이나 | 암흑 화염 옮겨 붙기 등 |

## 세 가지를 한 구조에 맞물리게 할 수 있는가

DDD, E+F+R, ECS 를 다 만족할 수 있는지 대 봤다. **할 수 있다. 다만 셋이 서로 다른
질문에 답한다는 것을 못 박아야 한다.**

| | 무엇에 답하는가 | 어디를 맡는가 |
| --- | --- | --- |
| DDD | 무엇이 함께 바뀌는가 | 쓰기 경계 |
| ECS | 상태를 어떻게 담고 행위를 어떻게 붙이는가 | 경계 안쪽의 담는 방식 |
| E+F+R | 담긴 것을 화면까지 어떻게 흘려보내는가 | 읽기 경로 |

경쟁이 아니라 쓰기 쪽과 읽기 쪽을 가르고, 쓰기 쪽 안에서 담는 방식을 정하는 것이다.

### 부딪히는 데 셋. 규칙으로 못 박는다

**하나. ECS 는 부품 저장소를 밖에 두려 하고, DDD 는 밖에서 손대는 것을 막는다.**

부품 저장소를 애그리게이트 안에 둔다. 시스템도 안에서 돈다. 밖에서는 명령만 넣는다.
지금 화면이 전투 상태를 직접 고치는 열여덟 곳이 이 규칙을 어긴 것이고, R2-97 에서 막는다.

**둘. ECS 의 엔티티는 번호뿐이라 도메인 말이 사라진다.**

유닛은 번호로 담되, 도메인 말은 애그리게이트가 낸다. 밖에서는 [얼었는가], [체력이
얼마인가] 로 묻는다. 그것이 안에서 부품 조회인지는 밖에서 안 보인다. 의미는 시스템
이름에도 남는다 — [빙결을 푼다], [암흑 화염을 정산한다].

**셋. E+F+R 은 매 틱 다시 만드는데, 연출은 제 그림을 스스로 들고 돈다.**

E+F+R 은 상태로 정해지는 것에만 쓴다. 체력 숫자, 에너지 수, 빙결 표시, 카드 자리.
연출은 그 밖이고 지금처럼 제 겹을 들고 돈다. R2-91, R2-92 에서 확인했다. 연출의
그림들은 저마다 제 박자로 움직여서 밖에서 자리를 고치면 다음 박자에 덮인다. 억지로
넣으면 다시 쓰는 일인데 얻는 것이 없다.

### ECS 를 성능 때문에 들이지 않는다

여기는 손패 한 페이지가 넉 장, 필드에 몇 장, 카드 하나가 그림 다섯이다. 캐시 친화성이나
병렬 처리로 얻을 것이 없다.

들이는 이유는 조합성 하나다. 카드가 300장이 되면 빙결, 암흑 화염, 소환 멀미 같은 상태가
수십 가지가 된다. 한 객체에 필드를 계속 붙일 수 없다. 지금 [카드 열두 장이 화면 마흔여섯
곳] 이 그 증상이다.

## 이름은 실제로 하는 것만 붙인다

**[DDD + E+F+R + ECS] 라고 부르면 안 된다.** 지금도, 계획대로 한 뒤에도 그렇다.

| | 이름값을 하는가 |
| --- | --- |
| DDD | **한다.** 순수한 도메인, 애그리게이트, 명령과 일어난 일이 실제로 있다 |
| E+F+R | **이름만 같다.** 여기 Frame 은 자리 규칙이고, 표현용 상태를 뽑는 층이 없다 |
| ECS | **없다.** 부품도 저장소도 시스템도 없다 |

계획대로 해도 ECS 는 온전히 하지 않는다. 전역 저장소를 안 쓰고, 스케줄러도 병렬도 안
쓴다. 조합성만 쓴다. 그것을 ECS 라고 하면 읽는 사람이 전역 부품 저장소와 매 틱 시스템
순회를 찾다가 없어서 헤맨다. Frame 에서 이미 같은 일이 났다.

정확히 쓰면 이렇다.

> **DDD 경계 안에서 부품으로 조합하고, 화면까지 단방향으로 흘려보내는 구조**

짧게는 [DDD + 부품 조합 + 표현 파이프라인] 이다. 세 이름을 그대로 쓰려면 최소한
[ECS 식 조합] 처럼 단서를 달아야 한다.

## Frame 이 두 뜻으로 쓰이고 있다

| 지금 이름 | 실제로 담는 것 | 새 이름 |
| --- | --- | --- |
| Frame | 카드가 화면 너비의 몇 분의 얼마, 무기 표시가 카드 어디에 붙나 | **Layout** |
| — | 이 유닛의 체력, 자리, 보임 여부 (지금 없는 층) | **Frame** |

여기 Frame 은 엔티티를 전혀 보지 않는다. 레이아웃 값이다. 표현용 상태를 뽑는 층이
없어서, 렌더러가 엔티티를 직접 읽고 메시를 만든 다음, 그 뒤로는 화면이 손으로 고친다.
그 [손으로 고치는 것] 이 화면 4,274줄이고 직접 고침 열여덟 곳이다.

## 경계를 건널 때 무엇만 건널 수 있는가

폴더에 무엇을 넣는가보다 이것이 중요하다. 폴더는 나중에 옮길 수 있지만, 경계를 건너는
것이 헐거우면 그 틈으로 계속 새는 길이 생긴다.

| 경계 | 건널 수 있는 것 | 건너면 안 되는 것 |
| --- | --- | --- |
| **명령** (밖 → 전투) | 밖에서 정해진 사용자의 뜻과, 그것을 가려내는 데 필요한 입력 | 도메인이 정할 수 있는 결과값 (피해량, 비용 등), THREE, 화면 좌표 |
| **전투** | 규칙 적용과 상태 변경 | 화면과 THREE 를 아는 것 |
| **일어난 일** (전투 → 밖) | 실제로 일어난 사실. 필요하면 전후 값 | 어떻게 보여줄지, 얼마나 걸릴지 |
| **읽기 모델** (전투 → 화면) | 사용자가 아는 말 — 내 손패, 상대 필드, 지금 차례, 지금 할 수 있는 것 | 부품과 저장소 내부 |
| **표현 상태 / 자리 규칙** | 화면에 그릴 값만 | 도메인 객체, THREE |
| **렌더러** | 표현 상태 → THREE | 도메인에 닿는 것 |
| **연출** | 일어난 일과 그릴 자리 | **상태를 바꾸는 것 일체** |

한 줄로 하면 이렇다. **화면은 도메인 객체를 받지 않는다. 경계를 건너는 것은 정해진
계약 타입뿐이다.** 연출도 경계를 건너므로 같다 — 유닛을 통째로 넘기면 안 되고, 무슨
일이 일어났는지를 넘긴다.

## 값을 어디에 두는가

이번에 [공격력] 하나를 놓고 확인했다. 카드 정보에 공격력을 박으려다가, 공격력을 바꾸는
카드가 이미 여섯 장 넘게 설명에 적혀 있는 것을 찾았다.

```
필드 위 유닛 하나에 공격력 10 을 부여합니다
모든 몬스터의 공격력을 10 올립니다
이번 턴 동안 HP 5, 공격력 5 를 증가시킵니다
상대 필드 유닛의 공격력을 모두 합한 만큼 증가시킵니다
```

마지막 것은 상대 필드를 봐야 정해진다. 카드에 적어 둘 수 있는 값이 아니다.

**고정된 사실은 정의에 둔다. 전투 중 지속되는 사실은 상태로 둔다. 지금 상황을 해석해서
나오는 값은 규칙이 정한다. 규칙에 필요한 사실은 도메인 안에서 얻을 수 있어야 한다.**

| 무엇 | 어디에 | 예 |
| --- | --- | --- |
| 고정된 사실 | 카드 정의 | 기본 공격력 10, 스킬 기본 피해, 종류, 등급, 종족 |
| 전투 중 지속되는 사실 | 유닛에 붙는 부품 | 지금 체력, 빙결, 암흑 화염, 자리, 임자. 끝나는 때가 있으면 그것도 함께 |
| 지금 상황을 해석해서 나오는 값 | 규칙이 계산 | 최종 공격력 |

**[도메인 안에서 얻는다] 를 [아무 데나 뒤져도 된다] 로 읽으면 안 된다.** 뜻은 이렇다.

> 규칙 판정에 필요한 사실을 화면이 계산해서 넘기지 않는다. 도메인의 규칙이 필요한
> 사실을 도메인 안에서 조회하거나 계산할 수 있어야 한다.

무엇을 통해 얻을지는 그 규칙이 실제로 요구할 때 정한다. 지금 [판의 형편] 을 담는 물건을
따로 만들어 둘 필요는 없다.

### 공격력을 바꾸는 여덟 장을 열어 보니 성격이 넷이었다

| 카드 문구 | 무엇인가 |
| --- | --- |
| 공격력 10 을 부여한다 (세 장) | 지속되는 사실. 붙으면 남는다 |
| 이번 턴 동안 5 증가 | 지속되는 사실. 끝나는 때가 있다 |
| 에너지를 1개 보유 시 5 증가 | 지금 상황을 읽어 정해진다. 에너지가 빠지면 사라진다 |
| 상대 필드 공격력 총합만큼 증가 | 시전할 때 정하는지 계속 보는지에 따라 **게임 규칙이 달라진다** |
| 공격력 절반만큼 본체에 피해 | 공격력을 바꾸는 것이 아니라 **읽는다** |
| 토큰이 공격력 15 로 소환된다 | 고정된 사실. 토큰 카드의 정의값 |

넷을 전부 `공격력 +5` 같은 숫자로 저장하면 셋이 깨진다. 에너지 조건은 에너지가 빠질 때
누가 그 숫자를 지울지가 없어 에너지를 건드리는 모든 자리가 이 카드를 알아야 하고, 이번 턴
것은 끝나는 때가 값에 안 담기며, 상대 필드 합은 기획이 먼저 정해야 하는 것이다.

**조건 자체를 결과 숫자로 확정해 저장하지 않는다.** 다만 조건부라고 늘 규칙인 것도 아니다.
[다음 공격에 +5] 처럼 수명이 분명한 것은 상태로 두는 것이 자연스럽다. **효과의 수명과
의미로 정한다.**

### 규칙이 무엇을 보고 정하는가

| 규칙이 보는 것 | 예 |
| --- | --- |
| 카드 정의 | 기본 공격력, 스킬 기본 피해 |
| 지금 상태 | 지금 체력, 붙어 있는 지속 효과, 든 에너지 |
| 지금 판의 형편 | 내 필드, 상대 필드, 지금 차례 |

[상대 필드 공격력 총합] 과 [공격력 절반만큼] 은 셋째 없이는 답이 안 나온다. **지금 도메인은
그 합을 못 낸다.** 유닛이 공격력을 안 들고, 카드 정보로 물을 수도 없다. 그래서 화면이 대신
계산해 명령에 실어 보내고 있다.

즉 R2-96 은 화면의 숫자를 도메인으로 옮기는 일이 아니다. **규칙을 판정하는 데 필요한
사실에 도메인이 닿을 수 있게 되돌리는 일이다.** 이것이 되어야 R2-97 에서 명령에서 피해량을
빼도 안전하다.

**파생값을 상태로 저장하지 않는다.**

부품에 `총 공격력` 을 두면 붙을 때·떨어질 때·턴이 끝날 때·상대 필드가 바뀔 때마다 다시
채워야 하고, 하나만 빠뜨려도 틀린 값이 남는다. 위 카드들 때문에 특히 위험하다. 성능 때문에
어쩔 수 없어지기 전에는 계산값으로 둔다.

**같은 뜻의 값이 두 곳 이상에 담기지 않는다.** 기본 공격력은 정의에, 지속되는 것은 상태에,
최종값은 계산으로 — 이건 정상이다. 카드 정의에도 있고 유닛에도 있고 화면에도 있는 것은
막는다. 지금은 지켜지고 있다. 에너지는 전투가 들고 화면은 그 위에 얹은 그림만 든다.

### R2-96 은 값을 옮기는 일이 아니다

> **공격력 항목을 도메인에 하나 더 다는 일이 아니다. 도메인이 게임 규칙을 판정할 수
> 있도록, 필요한 사실에 닿는 길을 되돌리는 일이다.**

지금 화면이 피해량을 계산해 명령에 실어 보내는 것은 화면을 만든 사람이 잘못 짠 것이
아니다. **도메인이 필요한 사실에 닿을 수 없어서 생긴 구조적 결과다.** 도메인에 유닛의
공격력이 없으니 상대 필드를 훑어 합을 낼 수가 없고, 그러니 화면이 대신 했다.

이 전환이 중요하다. 앞으로는 [이 값을 어디로 옮기지] 가 아니라 **[이 규칙은 누가
판정해야 하고, 그 판정자는 어떤 사실이 필요한가]** 를 먼저 묻게 된다. 그 질문이 나오면
명령·System·읽기 모델·연출을 가르는 일이 훨씬 덜 억지스러워진다.

### R2-96 이 끝났다고 말할 수 있는 조건

| | |
| --- | --- |
| 같은 뜻의 값이 두 곳 이상에 담기지 않는다 | |
| **규칙 판정에 필요한 사실을 화면이 계산하지 않아도 도메인에서 얻을 수 있다** | 상대 필드 공격력 합 같은 것 |

둘째가 핵심이다. 이것이 안 되면 R2-97 에서 명령에서 피해량을 빼는 순간 도메인이
[그래서 얼마인데] 상태가 된다.

## Battle 의 역할을 지금 제한한다

지금 `Battle` 이 439줄에 공개 메서드가 79개다. 줄 수가 문제가 아니라 **공개 메서드
79개가 냄새다.** 규칙은 처리기 607줄 안에 열넷이 들어 있다. 카드가 늘면 그 파일이 큰다.

| | 무엇을 맡나 |
| --- | --- |
| Battle | 이 명령을 이 전투에서 받을 수 있는가. 어떤 규칙을 어떤 순서로 적용하는가. 끝난 상태가 성한가 |
| System | 피해 규칙, 대상 규칙, 차례 규칙, 죽음 규칙, 에너지 규칙 |
| Part | 지금 상태 |

**규칙 하나에 System 하나로 기계적으로 쪼개지 않는다.** 변경 이유와 다루는 데이터가
함께 움직이는 것끼리 묶는다. 그리고 System 을 먼저 만들고 규칙을 끼워 넣는 것이 아니라,
지금 있는 규칙을 열어 본 다음 묶음을 도출한다.

| 명령이 계산된 값을 담는다 | 4 | 피해량을 화면이 계산해 명령에 실어 보낸다 |

마지막이 이미 깨끗한 것은 우연이 아니다. [상태는 연출을 기다리기 전에 다 바꾼다] 는
규칙이 이미 서 있어서다. 전투의 진실은 이미 바뀌어 있고 연출은 그것을 2초 동안
보여줄 뿐이다. 이건 건드리지 않는다.

## 폴더를 가르는 목적

폴더가 예뻐지는 것이 목적이 아니다. **폴더가 곧 의존 경계의 물리적 표현** 이고, 그래야
경계를 코드로 잴 수 있다.

지금은 `battle/` 아래가 한 줄이라 [이것은 순수해야 하는가] 를 파일을 열어야 안다.
가르고 나면 폴더 위치만 보고 아래를 전부 잴 수 있다.

| 무엇에서 무엇으로 | 되는가 |
| --- | --- |
| domain → ui | 안 된다 |
| domain → THREE | 안 된다 |
| ui → domain 객체 | 안 된다 |
| ui → 계약 (명령·일어난 일·읽기 모델) | 된다 |
| 표현 상태 → THREE | 안 된다 |
| 렌더러 → THREE | 된다 |
| 연출 → domain 상태 변경 | 안 된다 |

## 검사로 지킬 것

| 검사 | 지금 |
| --- | --- |
| domain → THREE | **통과** (파일 57개) |
| domain → 창·브라우저 | **통과** |
| domain → ui | 폴더를 갈라야 잴 수 있다 |
| ui → 도메인 상태 직접 변경 | **18곳 위반** |
| ui 전체 → domain 전체 | 폴더를 갈라야 잴 수 있다 |
| 연출 → 도메인 상태 변경 | **통과** |
| 명령이 계산된 값을 담음 | **4곳 위반** |
| System → 특정 화면 구현 | System 이 아직 없다 |

표현 상태·자리 규칙·렌더러·연출 **어느 것도** 도메인 객체를 직접 만지지 못한다. 폴더
위치만 보고 자동으로 잴 수 있게 하는 것이 목표다.

## 다 됐는지 재는 법

문서가 아니라 이것으로 판정한다. 새 카드 열 장을 넣어 보고 잰다.

| 무엇을 재나 | 통과 |
| --- | --- |
| 카드별 갈래가 늘었나 | 안 늘어야 한다 |
| 기존 카드의 정의를 고쳤나 | 안 고쳐야 한다 |
| 기존 카드의 연출을 고쳤나 | 안 고쳐야 한다 |
| 없던 규칙이 없는 카드인데 공통을 고쳤나 | 안 고쳐야 한다 |
| 없던 규칙이 필요한 카드라 공통을 늘렸나 | **늘려도 된다** |

마지막이 중요하다. 공통을 고치는 것 자체가 실패가 아니다. 없던 규칙이 실제로 나왔으면
공통이 자라는 것이 정상이다.

**기존 규칙으로 표현되는 카드는 카드 정의와 전용 연출만 더한다. 없던 규칙이 필요할
때만 공통 구조를 늘린다.** 카드 한 장 더했다고 이런저런 새 층을 만들기 시작하면 오히려
망한다. 다른 점이 실제로 보였을 때만 구조를 더한다.

줄 수만 세지 않는다. 새 카드 열 장에 기존 코드 세 줄만 바뀌어도, 그 세 줄이
`switch(cardId)` 면 실패다.

## 다섯 가지가 지켜지는가

| | |
| --- | --- |
| 새 카드 한 장 | 기존 카드의 코드를 안 고친다 |
| 새 연출 하나 | 상태를 보여주는 코드를 안 고친다 |
| 화면이 바뀌면 | 전투 규칙을 안 고친다 |
| 전투 규칙이 바뀌면 | THREE 코드를 안 고친다 |
| 버그가 나면 | 흐름의 어느 구간인지로 좁혀진다 |

마지막이 나머지 넷을 뒤에서 확인해 준다. [시체 폭발이 피해를 안 준다] 면 명령 → 전투 →
카드 능력 → 대상 규칙 → 피해 규칙 → 일어난 일까지만 본다. 화면이 이상하면 일어난 일 →
읽기 → 표현 상태 → 자리 규칙 → 렌더러로 간다. 연출이 이상하면 일어난 일 → 연출로 간다.

```
├── session/                지금 진행 중인 한 판을 들고 있는 곳 (지금 repository/)
└── ui/                     그리는 쪽 전부
    ├── animation/          스킬 자리, 나갔다 오는 약속, 공격 연출, 카드별 연출
    ├── layout/             ← 지금 frame/ 이 담고 있는 자리 규칙
    ├── frame/              ← 새로 생김. 엔티티에서 뽑은 표현용 상태
    ├── card/ hand/ field/ zone/ turn/ unit/ master_hp/ field_energy/
    ├── active_panel/ card_grid_popup/
    └── view/
```

규칙은 한 줄이다. **`domain` 은 `ui` 를 모른다. `ui` 와 `domain` 은 계약을 통해서만 만난다.**

방향 자체는 `ui` → `domain` 으로 흐른다. 다만 **화면이 도메인 객체를 직접 다루지는
않는다.** 건너는 것은 명령·일어난 일·읽기 모델 같은 정해진 계약뿐이다. [ui 는 domain 을
안다] 고 쓰면 유닛이나 부품을 직접 만져도 된다고 읽힌다.

### repository 는 이름이 아니라 하는 일을 보고 정했다

열어 보니 저장소가 아니었다. **지금 진행 중인 전투 하나를 메모리에 들고 있는 것** 이다.
`start` / `restore` / `getCurrent` / `end` 를 내고, 파일도 서버도 되돌리기 기록도 없다.

| 이름 | 뜻 | 맞는가 |
| --- | --- | --- |
| repository | 애그리게이트를 꺼내 오고 담는 곳 | 하나만 들고 있어 과한 이름 |
| store | 담아 두는 곳 | 담아 두긴 하나 [지금 것 하나] 임이 안 보인다 |
| **session** | 지금 진행 중인 한 판 | **맞다** |

나중에 서버에 붙으면 그때 진짜 저장소가 생긴다. 그건 `session` 옆에 새로 생기는 것이지
이 이름을 바꿔 쓸 것이 아니다.

## 옮기는 순서

원인이 앞, 결과가 뒤다. 그리고 앞의 것을 안 하면 뒤의 것이 중간에 막힌다.

| 번호 | 무엇 | 왜 이 자리인가 |
| --- | --- | --- |
| R2-95 | 아무 화면도 쓰지 않는 옛 전투 화면과 딸린 것을 지운다 | 죽은 것을 새 구조로 옮기지 않는다 |
| R2-96 | 규칙 판정에 필요한 사실에 도메인이 닿게 한다 | R2-97 의 선행. 지금 도메인은 종류·체력·등급·종족 넷만 알고, 상대 필드 공격력 합을 못 낸다 |
| R2-97 | 명령에서 계산된 값을 뺀다 | 얼마나 아픈지를 화면이 정하는 것을 없앤다 |
| R2-98 | 화면이 전투 상태를 직접 바꾸는 길을 없앤다 | 옛 길이 남으면 [이게 더 빠른데] 하며 다시 뚫린다 |
| R2-99 | 전투 안을 도메인·지금 판·그리는 쪽으로 가른다 | 폴더가 곧 경계다. 갈려야 경계를 코드로 잴 수 있다 |
| R2-100 | 처리기의 규칙을 System 으로 옮긴다 | 규칙을 관찰한 뒤에 묶는다. 먼저 만들고 끼워 넣지 않는다 |
| R2-101 | 읽기 모델을 세운다 | 한 덩어리로 만들지 않고 기능별·사용자 관점별로 나눈다 |
| R2-102 | 의존성 검사를 자동으로 돌린다 | 폴더가 갈린 뒤 |
| R2-103 | 새 카드 열 장으로 확장 시험 | 문서가 아니라 이것으로 판정한다 |
